- Confirmed: our automation deployments do not use CAPP GitOps sync. No GitOps deployment cleanup is part of D18. Archiving our script repository remains cascade step 4.
- Confirmed: each automation has its own registry image path. Step 3 can enumerate and delete versions within that path, excluding the shared golden base.

- Agreed: ordinary enable/disable changes matching only. Do not call CAPP PUT to toggle deployment traffic; existing runs may finish.
- Agreed: reject DELETE with `409` while a build/rollout is in progress, enforced server-side under the same admission lock as edit/build. Do not implement build cancellation inside D18.
- Agreed (2026-09-15, implementation): only the DELETE that moves the row to `deleting` launches the one background cascade attempt. A repeated DELETE returns progress (`202` while deleting, `200` once deleted) and starts nothing, so a UI that polls with DELETE cannot pile up concurrent attempts against CAPP. A stopped cascade is resumed only by the reconciler chain: E21 CronJob → D20 `POST /internal/automations/{id}/resume-delete` → `cascade.resume_delete`. Until E21 ships, a stopped cascade stays `deleting` until `resume_delete` is invoked.
- Agreed (2026-09-15, implementation — D14 readiness): no git (or later CAPP) I/O runs inside a DB transaction or under the automation row lock. Edit uses `build_state=building` as the lock (claim → commit to git with no session → finish only if the claim is still its own); create commits to git first, then inserts. Every `SELECT … FOR UPDATE` on an automation is bounded by `DATABASE_LOCK_TIMEOUT_MS` (2000 ms) and maps to `503` + `Retry-After: 1` instead of waiting into the 5 s statement timeout.
- Agreed: CAPP DELETE `204`, or confirmed target absence (`404`), completes deletion of a CAPP resource from our API's perspective — for both the Capp and the run-auth Secret. Proceed with the cascade without pod polling, fixed sleeps, or an extra termination grace period. This is an accepted API boundary, not proof that every running process has already stopped.
- Agreed: wallet management is external. Our code must not create/update/delete CAPP namespaces, quotas, or permission bindings as part of D18. Permission changes are neither an automatic action nor a prerequisite for declaring our automation cleanup complete.
- Agreed (revised 2026-09-15, supersedes the earlier env-var decision): one API key per automation, held in two places — (a) a **Keep-owned run-auth CAPP Secret** created with the Capp and mounted into it, which the wrapper reads to validate `/run` calls; (b) an **encrypted copy in our DB**, which the automation API decrypts to call `/run`. The two are one credential, so the delete cascade deletes the run-auth Secret and clears the DB copy together (step 2). Team-owned Secrets referenced through `secret_name` are a different thing and are always retained.

Implement matching enable/disable and an asynchronous, durable five-step deletion cascade in `keep-automation-api`. The cascade removes everything Keep created for the automation in external systems — the Capp, **the run-auth API-key Secret**, the encrypted DB copy of that key, and the registry images — and archives the script. Keep automation definitions, revisions, run history, and script bytes permanently. Deboarding is a thin business-logic loop that invokes that same cascade for every automation targeting a wallet; D18 exposes no deboard route.

- **Step 2c** clears `run_api_key_encrypted` only if the ORM table carries that column (resolved at call time); no code change is needed when D16/F24 add it. Tested against a stand-in nullable column.
- **Sanitized error codes** returned by `CascadeResult.error` and logged with the exception *type* only: `capp_delete_failed`, `run_auth_secret_delete_failed`, `registry_list_failed`, `registry_delete_failed`, `registry_inventory_not_empty`, `git_archive_failed`, `checkpoint_failed`, `cascade_no_progress`.
- **Pending runs** of a deleting/deleted automation are finalized `suppressed` + `suppression_reason=inactive` — a new enum value (never invoked, so not deletion-killed), matching the submit contract's "not active" reason. `submitted` → `failed` + `terminated_by_deletion`. Terminal rows are never overwritten.
- **Deboard summary semantics:** `deleted`; `in_progress` = admitted (`deleting`) but this pass stopped at a checkpoint; `skipped_building`; `failed` = deletion could not be admitted (row still active/inactive). Deboard, unlike a repeated user DELETE, does run the cascade for children already `deleting` — it is an explicit operator pass. Signature gained `actor` for the delete revision.
- **Authoring (D13 code touched for D14 readiness):** create/edit now stamp `building_sha` and `build_lock_deadline` (`AUTOMATION_BUILD_LOCK_TIMEOUT_SECONDS`, default 1800). The deadline is the edit claim's fencing token; an edit whose claim was released mid-commit (E21) returns `409` and writes nothing; a git failure restores the previous `build_state`/`building_sha`. Edit now bumps `updated_at`. A DB failure after a create's git commit leaves an unreferenced `{id}/script.py` (logged).
- **Redis config:** `REDIS_URL`, `AUTOMATION_RELOAD_CHANNEL` (default `reload`, same names as keep-event-handler), `REDIS_PUBLISH_TIMEOUT_SECONDS`; empty `REDIS_URL` → no-op publisher.
- **Contracts vendoring:** no vendored copy of `validation_errors.py` exists in keep-automation-consumer or keep-event-handler, so the change set is the canonical package + `automation-contracts.md` only.

**Resume is business logic here, a route in D20.** The D18 story lists "cascade resume endpoint shared with D20/E21" under *Interfaces*, and D20's story explicitly enumerates `…/resume-delete` in its §8.3 internal surface. Why it's needed: the DELETE background attempt (steps 2–5) can die — pod restart, CAPP/registry/git timeout — leaving the row stuck in `deleting`. `resume_delete` continues from the step after `delete_cascade_step` and returns current progress: `deleting` → continue; `deleted` → no-op; active/inactive → `LifecycleConflict` (D20 maps to `409`), never an implicit delete. A repeated user DELETE (route 3) does **not** reach the runner — it only reports progress (2026-09-15 decision), so `resume_delete` is the only retry path. Chain: D18 function → D20 route → E21 CronJob schedules it.

User operations derive tenant and actor from the session. Unknown and cross-tenant IDs both return `404`. Enable/disable on deleting/deleted return `409`; building alone does not forbid a toggle when the digest requirement is met.

Within a short row-locked transaction, change matching state, increment `index_generation` atomically, update timestamps/actor, and insert the relevant revision. For repeated enable/disable, keep the requested state and still bump/publish as D18 specifies; audit the accepted request. Repeated DELETE or `resume_delete` calls must not create duplicate delete revisions or rewind progress. Preserve the initial deleting actor through internal retries.

Publish the configured Redis `reload` signal only after commit. It is an invalidation signal, never a definition payload. Bound publisher latency; failure is logged and does not roll back a committed transition. A crash or failed publish is covered by B4’s unconditional 30-second reload and reconnect reload. Keep those backstops even after generation starts changing.

Expose lifecycle progress through GET detail, DELETE responses, and the `resume_delete` return value, without reading git merely to return a lifecycle acknowledgment.

**2. Implement exactly five durable cascade checkpoints**

Add `src/bl/cascade.py`. `delete_cascade_step` means **last completed step**: null means not begun; values 1–5 mean the following operations completed. Advance monotonically with conditional database updates. An external operation may execute again if its response or checkpoint commit is lost.

| Step | Operation | Replay and completion rule |
|---|---|---|
| 1 | Commit matching state `deleting`, generation bump, timestamp/actor, and one delete revision; attempt reload publication after commit. | State is the durable authority; reload is best effort. Replays can publish again without creating a new deletion transition. |
| 2 | Delete the CAPP deployment and its run-auth credential via D16: **2a** DELETE the Capp; **2b** DELETE the Keep-owned run-auth Secret; **2c** clear the encrypted DB key in the same transaction as checkpoint 2. | Order is fixed: Capp first (deleting the Secret under a live Capp could break restarting pods mid-run), then Secret, then DB. `204` or `404` is success for 2a and 2b. **Always run 2a and 2b, even when `capp_deployment_id` is null**: a first deploy may have created the Secret and then failed before or during Capp creation. Use the stored `capp_deployment_id` if set, otherwise the deterministic name `automation-{id}`; the Secret is always `automation-{id}-run-auth`. Auth failures and timeouts are not success: stop, keep checkpoint 1 and the DB key, and a retry re-runs 2a (now `404`) then 2b. Never delete the team Secret named by `secret_name`. No pod polling or termination wait. |
| 3 | Delete this automation’s registry image digests using A0 credentials. | Enumerate all owned image versions, including old/inactive and build artifacts; delete each if present. If interrupted partway, repeat safely. Advance only when the owned inventory is empty. |
| 4 | Archive-mark the automation’s script path in git via `GitClient.archive` (C4). | Deterministic marker (proposed `/{automation_id}/.archived`), no extra commit if already archived. Keep script bytes and history accessible; marker changes must not trigger a fresh image build (C3). |
| 5 | Commit matching state `deleted` and progress `5`. | Retain definition, revisions, runs, digest references, and archive evidence. Already deleted is a no-op. |

The DELETE request completes step 1 and launches one bounded background attempt for steps 2–5. Background work opens its own sessions and loads by ID; it never captures a request session. The database checkpoint is the durable work record, not the in-process task. Only the DELETE that performs the admission launches that attempt; repeated DELETEs report progress only. If the attempt stops or the task is lost, `resume_delete` (exposed by D20's internal route) continues it. E21 owns scheduled discovery/retry; D18 adds no independent recurring scheduler.

Each external operation runs outside pooled DB transactions, with explicit timeout and bounded concurrency. Stop on failure, retain the last successful checkpoint, and report a sanitized operation error in logs/internal response. A failed deletion remains `deleting`, never falsely `deleted`. Retry authentication through D16’s established refresh behavior; persistent `403` requires restored access or independently verified cleanup.

**3. Close build, invocation, and concurrent-resume races**

Use short row locks for admission and compare-and-set checkpoint writes. Two deletion runners may safely repeat an idempotent step; neither may regress a checkpoint or skip a predecessor. Correctness must work across API replicas, not depend on a Python mutex.

Deletion must also coordinate with D15/D16 deployment mutations. Reject new edits/build cutovers after deleting begins, and make late webhooks harmless. A state check immediately before a CAPP request is insufficient: a previously admitted create/rollout can finish after deletion and recreate resources (a Capp, a run-auth Secret, or both).

Keep the building guard active through CI completion and the associated CAPP create/rollout. Under the shared database admission lock, either a build wins and DELETE returns `409`, or deletion wins and edit/build admission fails. A UI-disabled button is only a convenience; the backend owns this rule. Repeated deletion of an already-deleting/deleted row follows its idempotent path first.

**No I/O under the admission lock (implemented 2026-09-15, D14/D15/D16 must keep it).** The row lock is held only for short DB-only transactions. Git, CAPP, and registry calls run with no session open. Operations that need exclusivity across I/O claim a durable state instead of holding the lock: edit claims `build_state=building` with a fresh `build_lock_deadline`, commits to git, then finishes in a second short transaction only if the row still carries that deadline (otherwise `409`, nothing written); a git failure restores the previous build state via compare-and-set on the same deadline. While claimed, DELETE sees `building` and returns `409` immediately — never a lock wait. D15's cutover and D16's create/rollout follow the same claim → call → finish shape via `lock_for_build_mutation`. Every lock acquisition sets `SET LOCAL lock_timeout` (`DATABASE_LOCK_TIMEOUT_MS`, 2000 ms, below the 5000 ms statement timeout) and maps `lock_not_available` to `503` + `Retry-After: 1`.

Do not clear the guard solely because its deadline elapsed while CI or a deployment mutation can still finish. D20/E21 owns stuck-build recovery; it must settle or fence late work before making deletion eligible (C2). The YAML exposes no operation-status endpoint, so do not invent one in D18. Test late callbacks explicitly. Each automation has its own image path (confirmed): enumerate every version there, not only `active_digest`, and never remove another automation's images or shared golden-base blobs.

**4. Integrate deletion-aware run finalization with D17**

Before initial invocation and each retry/re-drive, recheck durable lifecycle state. A queued request that has never invoked `/run` follows D17’s inactive suppression behavior. It is not a deletion-killed execution; it is recorded `suppressed` + `suppression_reason=inactive` (enum value added 2026-09-15, documented in contracts §DB enums).

For a disrupted in-flight call whose automation is deleting or deleted, commit `state=failed`, `failure_class=terminated_by_deletion`, and `finished_at`, retaining attempts and digest. Do not fabricate a wrapper outcome when none arrived. Stop retries and return the persisted terminal result to the consumer. Classification must work even if step 5 finished before the socket error arrives.

Do not bulk-finalize all submitted rows when CAPP returns `204`: an existing call may still return a valid success during platform shutdown. Live invocation owners persist the actual response, or classify a disrupted call as terminated by deletion. Step 2 and step 5 do not wait for these rows. Resolve pending, never-invoked rows as `suppressed` + `inactive`. For orphaned submitted rows, D20/E21 must use the existing overdue-run deadline and execution-ownership guard to finalize deletion termination without re-invoking a deleting/deleted automation; this is a shared repair contract, not a new D18 scheduler (C1).

Serialize terminal updates so an already-committed success or failure is preserved. Test the opposite race too: a late response cannot overwrite an already-committed deletion termination. Use one finalization/notification path; deletion termination must bypass ordinary team failure notices and script-failure dead-letter routing. The reworded “terminated by deletion” notice/UI text is derived from `failure_class`; no separate audit message field is stored. Preserve ordinary notifications for failures that completed before deletion.

**5. Deboard through the same cascade**

**Scope decision: minimal.** The story names deboard ("cascade all the wallet's automations") and spec §5.4 defines it as the same cascade fanned out, but neither pins an endpoint, a caller, or caller authorization, and D18's Verification/Done-when never test it. So D18 delivers only the fan-out function; it deletes Keep automations targeting a wallet and never touches the wallet itself.

Add `deboard_wallet(tenant_id, wallet_name)` in `src/bl/cascade.py` (or `src/bl/lifecycle.py`):

1. Select IDs of automations where `tenant_id = :tenant_id AND namespace = :wallet_name` and state is not `deleted` — served by spec §4.4's `(tenant_id, namespace)` index, which exists "for deboard fan-out". **Tenant is mandatory**: two tenants can target the same wallet name, and deboarding one must never delete the other's automations. Iterate all matches; do not reuse the authoring list's row limit.
2. For each ID, call the same single-automation delete admission + cascade runner used by route 3. No separate deboard cascade.
3. **Building child → skip and report.** Apply the same `409` build guard: the child is left untouched, reported as `skipped: building`, and deleted on a later call after its build settles. Do not cancel builds; do not block the rest.
4. One child failure does not stop the others; its checkpoint is retained and a later call resumes it.
5. Return a summary: `deleted`, `in_progress` (admitted, still `deleting` after this pass), `skipped_building`, `failed` (deletion could not be admitted). Empty target set succeeds. Repeated calls skip already-deleted children and resume incomplete ones — progress derives from the child rows, no deboard table or marker.

**Explicitly not in D18:** an HTTP route or CLI for deboard, its caller authorization, a wallet-level admission marker blocking new authoring during cleanup, multi-tenant wallet authority rules, wallet status changes, and any CAPP namespace/quota/permission mutation. Whoever adds the caller (F25 or ops) owns the entry point, its auth, and tenant boundary.

No D18 code changes permissions, asks the team to revoke access, or waits for revocation. Unexpected `403` is an ordinary external-operation failure: preserve progress and retry later; never treat it as proof of deletion. Each child's cascade deletes its own run-auth Secret; team-owned Secrets are preserved. Wallet registration, inventory sync, and E21 auto-disable remain outside D18.

**Agreed run-auth API key: CAPP Secret + encrypted DB copy — D16/F24 interface**

*Creation (D16/F24 — D18 depends on it, does not build it).* On first deploy, generate one random key (e.g. 256-bit) per automation and:

1. Persist it **encrypted in our DB** (new nullable column, e.g. `automations.run_api_key_encrypted`; migration in `keep-migrations`, ORM in the automation API). Encryption-key material stays outside the database.
2. `POST …/namespaces/{wallet}/secrets` a **run-auth Secret** with a deterministic name derived from the automation id — proposed `automation-{automation_id}-run-auth`, data key `api-key`. Deterministic naming means no extra column and the cascade can always find it.
3. Create the Capp with that Secret in `secretVolumes` at a fixed wrapper-owned path (proposed `/etc/automation/run-auth`; exact path pinned by F22/D16), **separate** from the team Secret mount at `AUTOMATION_SECRETS_PATH`.

The wrapper reads the key file at startup and validates the `X-API-Key` header on `/run`; missing/invalid header → `401`; missing/empty key file → fail closed. The automation API decrypts the DB copy to send the header. Rollouts reuse the same Secret and key; rotation must update Secret, DB copy, and roll the Capp together. Redact the key from logs, errors, traces, user responses, and audit payloads; never commit it to git or `.env`.

*Ownership guard — never delete a team Secret.* `caap.yaml`'s `SecretRequest` accepts no labels, and every API-created Secret (including team Secrets made through our secrets UI) carries the same CAPP managed label, so ownership can only be established by the reserved name. Therefore: (a) D13 authoring validation and the secrets UI must reject team Secret names matching `automation-*-run-auth`; (b) the cascade deletes **only** the exact name for its own automation id, never `secret_name`, never by listing or pattern.

*Deletion (D18, cascade step 2 — the API-key Secret is part of every delete).* 2a Capp DELETE `204`/`404` → 2b run-auth Secret DELETE `204`/`404` (`404` = already gone, or not a Keep-managed object — nothing of ours to remove) → 2c clear the encrypted DB key **in the same transaction** that commits checkpoint 2. If 2b fails (`401`/`403`/timeout/5xx), stop with checkpoint 1 and the DB key retained; the retry repeats 2a harmlessly. Both calls run even for an automation that never finished its first deploy (`capp_deployment_id` null), so a Secret left behind by a half-finished deploy is still removed. Never clear the DB key before both CAPP deletions succeed. Invocation caches, if D17 adds any, must respect deleting/deleted state; never reuse a cached key for a deleted automation. Clearing our copies does not erase a key already loaded by a terminating container — acceptable, since the Capp is gone.

*Team Secrets are retained.* The Secret named by `secret_name` belongs to the team and may be used outside Keep; a reference is not ownership. D18 makes no namespace or permission changes. The cascade stays at five steps: Secret deletion and DB-key erasure are sub-operations of step 2.
